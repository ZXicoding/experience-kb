# H5 本地模型部署 · 完整踩坑记录与经验总结

> 项目：把本地大模型（Ollama）部署成一个手机可访问的 H5 聊天应用
> 设备：Mac（Apple M5，24GB 统一内存，Metal GPU）
> 时间跨度：2026-10-10 ~ 2026-10-14
> 最终成果：像素风多模态聊天应用 + 图片处理工具箱 + 模型切换 + 手机扫码连接 + 一键启动

---

## 一、项目最终形态

一个零依赖（仅 Node.js 内置模块 + 系统 Python/Pillow）的本地 HTTPS 服务：

| 能力 | 说明 |
|------|------|
| 文字对话 | Markdown 渲染 + 代码高亮 + 流式输出 |
| 多模态 | 图片理解（qwen2.5vl 系列）、视频抽帧、语音输入/朗读 |
| 图片处理 | 缩放/裁剪/水印/格式转换/拼图/压缩（Pillow） |
| 模型切换 | 7 个模型动态列表 + 多模态标签 + 手机自动轻量化 |
| 手机连接 | HTTP(8080) + HTTPS(8443) 双端口、二维码扫码、短地址 |
| 一键启动 | `.app` 应用 + 自动生成二维码 + 开浏览器 |

## 二、踩过的坑（按时间顺序，共 18 个）

### 坑 1：`keep_alive=-1` 导致 Ollama 报错

**现象**：对话接口返回 `time: missing unit in duration "-1"`

**原因**：Ollama 新版对 `keep_alive` 参数要求带时间单位，裸 `-1` 不合法。

**解决**：改成 `-1m`（表示常驻内存）。这是 `.env` 里的 `KEEP_ALIVE=-1m`。

**教训**：升级工具后，之前能用的参数可能失效，报错信息里的「missing unit」是明确线索。

---

### 坑 2：Node 24 的 `Content-Length: undefined` 报错

**现象**：`TypeError [ERR_HTTP_INVALID_HEADER_VALUE]: Invalid value "undefined" for header "Content-Length"`

**原因**：反向代理转发 Ollama 响应时，把 `upRes.headers['content-length'] || undefined` 直接塞进了响应头。当上游没有 Content-Length（比如 chunked 传输）时，值就是 `undefined`，Node 24 会抛错（老版本会静默忽略）。

**解决**：只在 header 存在时才设置 `Content-Length`，流式响应用 `Transfer-Encoding: chunked`。

**教训**：Node 版本升级后，对 header 值的校验更严格，`undefined` 不能当 header 值。

---

### 坑 3：`url.parse()` 安全告警

**现象**：`DEP0169 DeprecationWarning: url.parse() behavior is not standardized...`

**原因**：用了 Node 废弃的 `url.parse()`。

**解决**：改用 WHATWG `URL` API（`new URL(req.url, base)`）。

**教训**：新代码别用 `url.parse`，直接用 `new URL()`。

---

### 坑 4：vendor 静态库 404（最隐蔽的坑）

**现象**：页面 CSS 能显示，但 Markdown 渲染、代码高亮、XSS 过滤全部失效，看起来「加载失败」。

**原因**：前端 HTML 引用 `./vendor/marked.min.js` 等库，但服务器只服务 `public/` 目录，而 vendor 库实际放在项目根目录 `vendor/`（不在 `public/` 下）。导致 4 个库全部 404。

**解决**：把 vendor 库复制到 `public/vendor/`。

**教训**：
- 静态服务器的根目录 = `public/`，所有前端引用的资源必须在它下面。
- 这种「部分资源 404」的 bug 很隐蔽，因为 HTML/CSS 能加载，只有 JS 功能悄悄失效。
- 排查方法：逐个 `curl` 检查静态资源状态码。

---

### 坑 5：夸克浏览器不支持 `fetch` 流式读取

**现象**：电脑 Safari/Chrome 能流式对话，但夸克里发消息「没有反应」。

**原因**：夸克桌面版对 `fetch` + `resp.body.getReader()` 的流式响应（SSE）支持有问题，读不到数据。

**排查过程**：
1. 先加了后端请求日志，发现请求其实到达了后端（`POST /api/chat auth=ok`），token 也正确
2. 但前端 `getReader()` 一直卡住拿不到数据
3. 证明是前端流式读取的问题，不是后端

**解决**：改用 `XMLHttpRequest` 的 `onprogress` 事件读取流式数据（兼容性最好）。

**教训**：
- 「模型没反应」要先分清是「请求没发出去」还是「响应读不到」，加后端日志是关键。
- 流式读取方案要兼容性优先，`XHR onprogress` 比 `fetch getReader` 更稳。

---

### 坑 6：夸克缓存旧代码

**现象**：改了代码，夸克里刷新后还是旧行为。

**原因**：`app.js` 的缓存策略是 `public, max-age=3600`（1 小时），夸克缓存了旧版本。

**解决**：静态文件全部改成 `Cache-Control: no-store`（开发阶段）。

**教训**：开发阶段禁止缓存，否则「改了不生效」会浪费大量排查时间。用户要强制刷新（Cmd+Shift+R）。

---

### 坑 7：前端发图片时 Ollama 报 base64 错误

**现象**：`json: cannot unmarshal string into Alias.images.0 of type api.ImageData: illegal base64 data at input byte 4`

**原因**：前端用 `canvas.toDataURL('image/jpeg')` 得到的是 `data:image/jpeg;base64,xxxx`（带前缀的 data URL），但 Ollama 的 `images` 字段要求**纯 base64**（不带前缀）。`data:` 这几个字符不是合法 base64，所以报 `illegal base64 data at input byte 4`（第 4 个字节）。

**解决**：发送前剥离 `data:...;base64,` 前缀，只发纯 base64。前端 + 后端各做一层防御（后端 sanitizeMessages 也剥离）。

**教训**：
- data URL 和纯 base64 是两个概念，接口对接时要明确。
- 报错里的 `at input byte 4` 提示了「前几个字符就错了」，是定位关键。

---

### 坑 8：模型「生成照片」误解

**现象**：用户让模型「生成照片」，模型报错或做不到。

**原因**：接的 qwen2.5vl 系列是**多模态理解**模型（看图说话），不是**图像生成**模型（文生图）。

**解决**：澄清概念——理解图片 ≠ 生成图片。图像生成需要 Stable Diffusion / Flux 等完全不同的模型。

**教训**：多模态有两个方向（理解 vs 生成），要先和用户对齐需求。

---

### 坑 9：32b 大模型超出 24GB 设备内存

**现象**：下载了 `qwen2.5vl:32b`（21GB），但跑起来后占用 30GB（含 65536 上下文的 KV cache），系统内存只剩 9%，推理极慢（300 秒没返回一句话）。

**原因**：21GB 模型 + 大上下文的 KV cache 超过 24GB 物理内存，被迫 51% CPU / 49% GPU 混合运行，还触发磁盘换页（pageouts）。

**解决**：
- 手机/日常用 3b（3.2GB，100% GPU，流畅）
- 桌面用 7b（6GB，100% GPU）
- 32b 保留但**不建议在这台设备上用**（除非关掉其他模型）

**教训**：
- 选模型要匹配设备内存，统一内存 ≠ 无限内存。
- `ollama ps` 能看实际占用（含 PROCESSOR 的 CPU/GPU 比例），是判断「带不带得动」的关键。
- 判断基准：模型体积 + 上下文 KV cache 才是真实占用。

---

### 坑 10：手机浏览器部分能开、部分打不开（证书信任）

**现象**：Safari/Chrome 能打开 HTTPS，但夸克/UC/微信内置浏览器打不开。

**原因**：自签名 HTTPS 证书在不同浏览器的信任策略不同：
- Safari/Chrome/Edge：弹警告，但给「继续访问」选项 → 能开
- 夸克/UC/360/微信：强制拦截自签名证书，不给绕过选项 → 打不开

**解决**：手机安装 CA 根证书（一劳永逸），或改用 HTTP 端口（绕过证书）。

**教训**：自签名证书是「跨浏览器不一致」的根源，要提供 HTTP 兜底 + 证书安装两条路。

---

### 坑 11：macOS 钥匙串「不能修改系统根证书」

**现象**：双击 `.crt` 导入证书时，系统提示「不能修改系统根证书钥匙串」。

**原因**：`.crt` 文件双击导入时，macOS 默认把它当成**系统级根证书**处理，而修改系统钥匙串需要更高权限。

**解决**：改用「钥匙串访问 → 文件 → 导入项目」，明确选择「登录」钥匙串（不是「系统」）。

**教训**：`.crt` 双击导入会走「系统」钥匙串，要用「导入项目」手动选「登录」。

---

### 坑 12：macOS 沙箱拦截 `security` 命令

**现象**：`security add-trusted-cert` / `security import` 报 `Operation not permitted`。

**原因**：DSH 的 bash 运行在文件沙箱里，默认没有访问钥匙串的权限。

**解决**：用户手动开通 `danger-full-access` 权限后，`security import` 和 `add-trusted-cert` 才能成功。

**教训**：
- 修改钥匙串是「系统级敏感操作」，需要更高的文件策略权限。
- 权限不足时，`security` 命令会静默失败，要检查 `Operation not permitted` 这类报错。

---

### 坑 13：证书缺少 CA 基本约束，iOS 无法信任

**现象**：准备给手机装证书时，发现原证书没有 `Basic Constraints: CA:TRUE`，iOS 无法作为根证书安装信任。

**原因**：最初生成的是普通服务器证书，不是 CA 证书。

**解决**：重新生成完整证书体系：
- CA 根证书（`CA:TRUE` + `keyCertSign` + `subjectKeyIdentifier`）
- 服务器证书（由 CA 签发 + SAN + `serverAuth` EKU）

**教训**：要给手机装信任，必须有独立的 CA 根证书，且带完整扩展。

---

### 坑 14：证书缺 SKI/AKI，iOS 可能拒绝

**现象**：检查发现 CA 证书缺 `Subject Key Identifier`（SKI）扩展。

**原因**：`openssl req -x509` 默认不带 SKI，需要 `-addext "subjectKeyIdentifier=hash"`。

**解决**：重新生成带 SKI/AKI 的证书。

**教训**：iOS 对证书扩展要求严格，SKI/AKI 是隐式必需的，生成时就要加上。

---

### 坑 15：手机 HTTPS「网络错误」但页面能打开

**现象**：手机用 HTTPS 能打开页面（点了「继续访问」），但发消息显示「网络错误」/模型不回复。

**原因**：这是最典型的坑——
1. 页面加载时，用户手动点了「继续访问」绕过证书警告，所以 HTML/JS 能加载
2. 但 JS 发起的 XHR/fetch 请求，浏览器会**重新校验证书**，此时没法再手动确认，被静默拦截
3. 前端 `xhr.onerror` 触发，显示「网络错误」

**解决**：
- 短期：改用 HTTP 端口（8080），不校验证书
- 长期：手机装 CA 证书

**教训**：
- 「页面能开但功能不能用」是证书问题的典型特征——页面加载和 API 请求的证书校验是分开的。
- 排查关键：看后端日志里有没有收到 `/api/chat` 请求。没收到 = 请求在浏览器层被拦截了。

---

### 坑 16：鸿蒙浏览器不下载 `.crt` 证书

**现象**：鸿蒙点证书下载链接，提示「在浏览器中打开下载证书的页面」，而不是下载文件。

**原因**：鸿蒙浏览器不认 `application/x-x509-ca-cert` 这个 MIME 类型，把证书（文本 PEM 格式）当成网页内容尝试打开。

**解决**：
- 改 Content-Type 为 `application/octet-stream`（强制下载）
- 改后缀为 `.cer`
- 更进一步：用 JS `fetch + Blob + a.download` 方式触发下载，彻底绕过浏览器对证书链接的特殊处理

**教训**：移动端浏览器（尤其鸿蒙）对「证书类文件」的下载处理很特殊，纯 HTML 链接下载不可靠，要用 JS Blob 方式。

---

### 坑 17：鸿蒙 7.0 找不到「安装证书」入口

**现象**：证书下载成功了，但在鸿蒙 7.0 设置里找不到「加密与凭据」「安装证书」这些菜单。

**原因**：鸿蒙 7.0（HarmonyOS NEXT 之后的新版）菜单结构和传统安卓差异大，证书安装入口藏得很深或改了名字。

**排查思路**：
- 设置里搜索：证书 / CA / 加密 / 凭据 / 安全证书
- 直接在文件管理器里**点 .cer 文件**（鸿蒙/安卓通常会自动弹出安装向导）

**教训**：鸿蒙版本迭代快，证书安装路径不稳定，要提供「文件管理器直接点文件」这种不依赖菜单的兜底方案。

---

### 坑 18：`.command` 文件双击无法启动

**现象**：双击 `.command` 文件启动服务失败。

**原因**：macOS 对 `.command` 文件的默认打开关联不稳定（可能用文本编辑器打开，或被 Gatekeeper 拦截）。

**解决**：改用 AppleScript 编译成原生 `.app` 应用（`osacompile`），双击体验和普通 App 一样，再 ad-hoc 签名。

**教训**：`.command` 不可靠，`.app` 才是 macOS 上「双击即用」的正确形态。

## 三、经验教训总结（核心规律）

### 1. 诊断要「分层定位」

最有效的方法是**逐层排查，别瞎猜**：
```
手机浏览器 → 局域网网络 → 后端服务 → Ollama
     ↑ 先确认请求到达了哪一层
```

关键手段：**后端加请求日志**（`console.log` 每个请求的方法/路径/鉴权结果），能立刻判断「请求有没有到后端」。

### 2. 证书是移动端最大的坑

自签名证书带来了一连串问题（浏览器不一致、iOS 扩展要求、鸿蒙下载、鸿蒙安装）。核心教训：

- **永远提供 HTTP 兜底**（不校验证书，任何设备立刻能用）
- HTTPS + 证书是「安全增强」，不是「必须」
- 手机装证书要做成「引导页 + 多格式下载 + JS Blob 兜底」的完整链路

### 3. 流式/缓存/兼容性要「兜底思维」

- 流式读取：`XHR onprogress` 比 `fetch getReader` 兼容
- 缓存：开发阶段一律 `no-store`
- 非流式接口兜底：流式不行就退非流式（但要注意兜底逻辑本身的 bug，见下）

### 4. 兜底逻辑本身要简单可靠

之前做的「流式 + 3秒超时退非流式」的 `Promise.race` 兜底逻辑，在手机上出现了「卡住不出结果」的问题。最终**直接改成非流式接口**（牺牲打字机效果换稳定性）。教训：

**复杂的兜底逻辑可能引入新 bug，不如直接选最可靠的方案。**

### 5. 模型要匹配设备

- 24GB 内存 → 3b（流畅）/ 7b（标准）/ 32b（勉强，会内存吃紧）
- `ollama ps` 看真实占用（含 CPU/GPU 比例）是选型依据
- 手机端自动切轻量模型（按 UA 识别）

### 6. 数据格式要对齐

- `data:image/jpeg;base64,xxx`（data URL）≠ `xxx`（纯 base64），接口对接要明确
- Ollama `images` 字段要纯 base64

### 7. macOS 系统级操作受权限限制

- 钥匙串修改需要 `danger-full-access` 权限
- `.command` 双击不可靠，用 `.app`
- Swift 编译要指定 `-module-cache-path`（沙箱下默认缓存路径不可写）

## 四、项目架构速查

```
ollama-h5/
├── server.js          # 主服务（HTTPS 8443 + HTTP 8080，零依赖）
├── image_process.py   # 图片处理（Pillow）
├── qr.swift           # 二维码生成（Core Image）
├── start.sh           # 启动脚本
├── 启动本地模型.app    # 双击启动的应用
├── certs/
│   ├── ca.crt/.key    # CA 根证书（手机安装信任用）
│   └── server.crt/.key # 服务器证书（SAN 含局域网 IP）
├── public/
│   ├── index.html     # 主界面（像素风）
│   ├── app.js         # 聊天逻辑（非流式为主）
│   ├── tools.js       # 图片处理 + 手机连接弹窗
│   ├── qrcode.js      # 备用纯 JS 二维码
│   ├── cert-guide.html  # 证书引导页
│   ├── download-cert.html # 证书下载页（JS Blob）
│   └── vendor/        # marked/highlight/purify
└── .env               # 配置（端口/模型/token）
```

**关键端口**：
- `8443` = HTTPS（需装证书）
- `8080` = HTTP（无证书，任何设备可用）

**关键模型**：
- 桌面默认 `qwen2.5vl:7b`
- 手机默认 `qwen2.5vl:3b`（自动切换）

## 五、给后续维护的建议

1. **换局域网 IP 后**：重新生成证书 SAN + 重新生成二维码（或写个自动重签脚本）
2. **换模型**：改 `.env` 的 `DEFAULT_MODEL` / `MOBILE_MODEL`
3. **手机装证书入口变了**：优先「文件管理器直接点 .cer 文件」这个不依赖菜单的方式
4. **排查「没回复」**：先看后端日志有没有收到 `/api/chat` 请求
5. **流式效果**：当前用非流式（稳定优先），想要打字机效果可后续加回（但要保留非流式兜底）
